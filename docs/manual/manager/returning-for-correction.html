Returning a request for correction

Sending a request back with a reason, and what the requester sees next.

Returning hands a request back to the person who raised it, with a message saying what needs fixing. They correct it and send it again; it comes back to you with the same number and the whole history intact.

It is the right decision for anything that is wrong rather than unwanted — the wrong head, a missing invoice, a figure that does not match the paperwork. Prefer it to rejection whenever the request could be made right, because rejection cannot be undone.

Returning a request

  1. Open the request and satisfy yourself that the problem is fixable.
  2. Select Return for correction.

    The panel that opens says who can act next: the requester can edit and resubmit, and the number and history stay.

  3. Write in What needs correcting. This is required, and the placeholder is a fair warning — Be specific — this is the whole message they get.
  4. Select Return request.

    You land back on the approvals queue and the request has left the To approve tab.

The panel, field by field

The return panel.
FieldWhat it is for
What needs correctingRequiredThe message the requester receives, word for word. A blank one is refused. It is recorded in the history, so everybody on the request sees it.

Name the field and the fix. Booked to Office Rent — this is a training cost, please move it to Training and Development tells the requester exactly what to change. Wrong head does not.

What the requester sees

The request moves to returned. It leaves your queue and reappears on the requester's home screen under Needs your action, carrying your message. They can edit it and submit it again, at which point it comes back to pending and to you.

Nothing about the request is lost in the round trip: the number, the thread and every earlier decision stay on it. Your message stays in the history too, so anybody reading the request later can see why it went back.

A returned request does not appear on the Decided tab of your queue. Decided holds only approved, rejected and cancelled requests. A returned one is genuinely still in flight.

If you are unsure which you want, return it. A returned request can still be rejected later; a rejected one cannot be brought back. Rejecting a request covers the other half.

Can I return a request more than once?

Yes, as often as it needs. Each round trip is recorded in the history, so a request that keeps coming back is visible for what it is.

I returned it by mistake. Can I pull it back?

Not directly — the request is with its requester now. Ask them to submit it again, and leave a comment in the thread saying why.

The requester says they never got the message.

It is on the request, in the History and conversation stream, which everybody who can see the request can read. Whether an email also went out depends on how your organisation has set up notification rules.
