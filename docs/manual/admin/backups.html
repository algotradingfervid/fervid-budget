Manual / Administration

Backups

Create a server copy and give the operator enough information to test a restore.

Create a backup

  1. Open Backups and select Create Backup.
  2. Confirm the action.
  3. Find the new entry and its readable creation time and folder.

Each copy contains the database, uploaded documents and manifest. The screen identifies files present; that is not a claim that a restore has been tested. Keep server configuration and secrets separately.

Recover through the operator

The page gives operator contact, the server folder, and a per-backup restore command. There is no browser restore action. Hand the operator the exact backup folder and the recovery date you intend.

  1. Agree the rollback point. Restoring replaces the current database and attachments with the backup's state.
  2. Have the operator preserve the current database, WAL/SHM files and attachments for rollback, then stop the application.
  3. Restore to a staging location and verify the selected copy before replacing production. Use the command and paths shown on the backup screen for the deployed environment.
  4. Restart and verify representative requests, budgets, payments and attachment downloads before resuming work.

The operator command uses the supported server --restore path with explicit database and attachment destinations. Do not substitute guessed production paths.

Copies and retention

The copy contains sensitive records regardless of the in-app viewer's permissions. Control access to the backup folder. The normal backup destination is on the same server, so an off-machine copy remains an operator responsibility.

Automatic schedules and retention are configured on the server. An entry disappearing after its retention window does not mean somebody changed the underlying financial record.
