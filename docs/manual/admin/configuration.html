Manual / Administration

Configuration

The settings that change how the product behaves for everybody.

Configuration holds the rules the request module runs on. The line under the heading makes the claim the screen is built around: everything here is data, so changing how the product behaves does not need a code change.

These settings are company-wide. There is nothing per-person and nothing per-project — a change here changes the product for everybody, from their next page load onwards.

The screen

Six fieldsets, top to bottom: Request numbering, Attachments, Urgency, Approvals, Payments, and Reminders and ageing. One Save configuration button at the foot covers all six. Discard leaves without saving.

Below the save bar sits a seventh block, Recoverable categories, which is not part of the same form and has its own page: Recoverable categories.

The note beside the buttons is worth taking at face value: "Every change here is written to the audit log." Anything you change is attributable, with a before and an after — see The audit trail.

Request numbering

How a request number is built. The seeded shape is PR-2026-000036.

FieldWhat it is for
PrefixOptionalThe letters at the front. Seeded as PR.
Year segmentOptionalCalendar year, Financial year or None.
Number widthOptionalHow many digits the running number is padded to. Seeded as 6.

Existing numbers are not reissued

Changing the numbering changes new requests only. Everything already numbered keeps the number it was given, so a change mid-year leaves two shapes of number in the system. Change it at a year boundary if you can.

Attachments

FieldWhat it is for
Require a supporting document on every requestOptionalTurning it on does not block submission. The hint explains why: it asks for an exception reason when no document is attached, because legitimate documents are sometimes genuinely unavailable.
Maximum file size (MB)OptionalThe largest file the product will accept. Seeded as 10.

Urgency

FieldWhat it is for
Marking a request urgentOptionalRequires a reason, Free to mark, no reason, or Disabled.

What urgency does not do

The note under the block draws the line the setting cannot cross: "Urgent requests follow the same approval rules. Urgency changes who is told and how soon, never who may decide."

Approvals

FieldWhat it is for
Let the employee choose a different approverOptionalOn by default. Off means everyone must use the default approver set on their user record — see People and accounts.
Block self-approvalOptionalTicked and greyed out. It is always on: a person can never approve a request they raised, whatever roles they hold. There is nothing to change.
Second approval above a thresholdOptionalGreyed out and unticked. The hint says it is reserved for a future version, and that the status model already has room for it. It does nothing today.

Payments

FieldWhat it is for
Allow direct payments without a requestOptionalOff by default. The hint states what turning it on costs: every new payment normally starts from an approved request, and switching this on demands a written reason and is flagged in the audit log.
Payment modes offeredOptionalComma separated, in the order the payment form should offer them. Seeded as NEFT, RTGS, UPI, Cheque, Cash, Card, DD.

Direct payments

A payment without a request is a payment nobody approved. Leaving Allow direct payments without a request off is what keeps the approval trail unbroken, and it is off for that reason. Turn it on only if you have a process for reviewing what comes through it.

Reminders and ageing

FieldWhat it is for
Remind after (days pending)OptionalHow long a request may sit with an approver before the first reminder. Default 3.
Then repeat every (days)OptionalHow often the reminder returns while nothing happens. Default 1.
Reservation goes stale after (days)OptionalHow long an accountant may hold a reservation with no payment recorded. Default 1.

How the counting works

The note under the block covers two things people get wrong: reminders are counted in calendar days, not working hours, and a request put on hold is waiting on the requester by design and is never reminded about.

Leaving one of these blank or setting it to zero does not switch reminders off — the default is used instead. Reminders cannot be disabled by accident from this screen.

Saving

  1. Change what needs changing, in any of the six blocks.
  2. Select Save configuration.

    All six blocks are saved together, and the change is written to the audit trail.

Change one setting at a time and watch what it does. These are company-wide switches, and a save that changes four of them at once leaves you guessing which one caused the phone calls.

Who can change it

Opening this screen needs the configuration view grant and saving needs the edit grant; both sit in the Administration row of Roles and permissions. The Recoverable categories block at the foot follows the Recoverables row instead, which is why somebody can be able to see the settings and not touch the categories, or the reverse.

I saved and nothing looks different.

Most of these settings show up on somebody else’s screen rather than yours — the request form, the payment form, the reminder that goes out tomorrow. Reload the screen the setting governs.

Why is Block self-approval greyed out?

Because it is always on. It is drawn ticked and disabled so the screen is honest about the rule rather than silent about it.

Can I set a different approval threshold for large amounts?

Not yet. Second approval above a threshold is drawn on the screen but marked as reserved for a future version, and it does nothing today.

Where are the recoverable categories?

At the foot of this screen, below the Save configuration bar. They have their own page: Recoverable categories.

Where are the email settings?

On Notification rules and email, not here.
