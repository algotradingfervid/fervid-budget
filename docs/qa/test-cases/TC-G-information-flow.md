# TC-G — Information-flow integrity

**Area.** Whether a fact entered at one end of Fervid Budget arrives intact, and
only where it should, at the other. Not *does the action work* — the sibling
suites ask that — but *does the data survive the journey, and does it leak*.

**Spec under test.** `docs/qa/uml/03-sequence-diagrams.md` §"Information-flow
integrity table", rows **IF1–IF12**, which name the datum that must survive each
flow and the field name it wears at every hop. Every case below traces to one or
more of those rows plus the coverage-matrix IDs in
`docs/superpowers/specs/2026-07-25-payment-requests-coverage.md`.

**Executable.** `tests/e2e/audit-g-information-flow.spec.ts` — every TC ID below
is the name of a test in that file.

```
FERVID_E2E_PORT=4307 npx playwright test tests/e2e/audit-g-information-flow.spec.ts --project=chromium --reporter=line
  56 passed (2.1m)
```

**Verdict counts.** 54 `PASS` · 2 `FAIL (product defect)` annotated `test.fail()`
so the suite is green while the assertion stays at full strength · 0 `BLOCKED` ·
0 `NOT RUN`. The two annotated cases are **TC-G-084** (F-G-027, an FK violation
answers 500) and **TC-G-090** (F-G-036, a letters-only password answers 500).
Playwright counts an expected failure as passed, which is why the line above

**Findings raised.** 34, in `docs/qa/results/findings-g-information-flow.md`
(F-G-001 … F-G-037, non-contiguous — the numbering was allocated during the

## Conventions used by every money assertion

`money.FormatPaise` (`internal/money/money.go:36-45`) already contains `₹`, so
every hop is asserted for the exact string **and** for exactly one `₹` glyph. A
double-format bug renders `₹ ₹1,00,000.00` and is caught at the hop that
introduces it, not three screens later. Amounts inside a `.money-field` input
carry no glyph at all — the field draws its own in a `.cur` prefix and the input
holds `amountValue` output (`internal/app/requests.go:1051-1057`), so those hops
assert the ungrouped-of-₹ form.

Each money journey owns a calendar month nobody else writes to (the e2e seed
budgets `2026-06` alone), which turns "the grid followed the money" from a delta
into an equality: the company total for that month **is** the payment.

## Detail — the three money journeys

The three cases at the head of the table are the substance of this suite, and
they are deliberately long rather than many. TC-G-001 asserts one figure at
eighteen consecutive hops; twelve independent checks of twelve screens would not
have caught a hop that silently substitutes a *different* correct-looking figure,
because each check would have had nothing to compare against.

TC-G-003 is the case that distinguishes the two figures the system has to keep

approved and the CSV has no column for the one they did.

## Detail — what "no audit row" was asserted against

TC-G-023, TC-G-024 and TC-G-025 are the negative half of C2, and each was made
exact rather than approximate. `/audit` applies its 1000-row window *before* the
actor filter (`internal/app/app.go:1368-1385`), so on a long run a subject's rows
can fall out of view and an absence assertion can pass for the wrong reason. Each
of the three therefore reads `/audit?entity=payment_request&id=<id>&actor=<name>`,
which narrows the SQL itself, and TC-G-024 additionally keys on an amount unique
to that test (`₹99,999.00`) so the assertion cannot be satisfied by a window
shift. All three confirmed that `recordAuditTx` rides inside the same
transaction as the mutation it describes, and that every guard returns before any
write.
