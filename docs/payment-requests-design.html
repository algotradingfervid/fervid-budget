Summary

At a glance

A request layer sits in front of the payment-recording Fervid Budget already does. Any employee raises a request against existing projects and heads; a manager approves it; Accounts record the real payment and link it; the request tracks to completion.

Who  Requester · Manager · Accounts · Admin Access  fine-grained, per screen, data-level Approval  requester picks the manager Linking  one request → one payment Settlement  Accounts confirm; short pay → manager review Money  budget expense vs recoverable
Foundational rule

Going forward, every payment must originate from an approved request — there is no direct-entry path. Payments recorded before go-live remain untouched as historical records.

01 The journey

End-to-end workflow

One request moves left-to-right through three sets of hands. The manager can approve (adjusting the amount if needed), return it for edits, or reject it. Accounts reserve it, record the payment, and declare it either settled or a genuine partial — the only case that returns to the manager.

02 People

Roles & permissions

Access is not four hard-coded roles — it's an admin-managed, per-screen permission system, ERP-style. Administrators create roles, tick exactly what each can do, and set how much data each can see. The three starter roles below ship pre-configured.

Starter roleCan doData scope
RequesterRaise, edit, withdraw, re-raise, comment on requests; add attachmentsOwn requests only
ManagerApprove / adjust / return / reject; accept partial; reassign; commentAll requests (approves ones routed to them)
AccountsReserve & process; record payment; settle / mark partial; place on holdApproved requests + payment ledger
AdminEverything, plus roles, users, categories, notificationsAll · combines with any role
  • Granular actions per resource: view, create, edit, approve, cancel, process, export, configure — whatever's relevant to that screen.
  • Data scope per resource: own only / assigned to me / all.
  • Multiple roles per user — access is the union; a person can be Requester + Manager.
  • Create-by-copy — duplicate a role, then adjust, to make new ones quickly.
Non-negotiable

Permissions govern the data on the server, not just which menu items show. A Requester cannot reach another person's request even by URL.

03 The form

Raising a request

The employee first chooses the financial treatment, then the type within it. The type decides the required fields and who the payee is. Bank details never appear here — Accounts hold those through existing controlled records. The form is mobile-first.

Figure 2. Treatment-first. Every request also carries amount, purpose, required-by date, chosen manager, and an optional Urgent flag.

Always captured

Auto request number (PR-2026-000123), financial treatment, type, amount, purpose, required-by date, approving manager, urgent flag.

Attachments

Not mandatory now — an employee may submit without a document. An admin config toggle can make them mandatory later.

04 Money you get back

Recoverable payments

Deposits and loans — EMD, PBG, ICD, security deposits, refundable employee advances — are money the company expects back, not expenses. We keep them out of the project/budget lists entirely rather than inventing fake projects for them.

  • Excluded from budget actuals; shown in a separate Recoverable payments report/total.
  • Admin-configurable categories (add new ones later).
  • Records counterparty/employee, reason, expected return date, repayment/refund notes. May still link to a real project (EMD/PBG require one; ICD requires the counterparty company).
  • The request closes once its outgoing payment is made, keeping its recoverable classification and expected-return info for reporting.
Why separate

Recoverables are contractual rights to receive cash — financial assets, not spend. Folding an EMD into a project budget would both overstate expenses and lose the deposit's link to the real work.

06 The money

Reserve, record & settle

One reservation, two doors

Accounts reach a payment two ways — a Create payment button on the request, or picking the request from a dropdown on the payment form. Either way the system atomically reserves the request and flips it to Processing. The dropdown lists only approved · unclaimed · not on hold requests, searchable by request number, requester, payee, project, head, and amount. Two accountants racing for the same request → the second sees "just taken by [name]." Cancelling or switching releases a reservation only after an explicit "no payment was initiated" confirmation.

Settlement is a decision, not a subtraction

When Accounts record the amount paid, they declare the outcome — the system does not guess it from the numbers:

Accounts clickConfirmation popupResult
Payment settledShows approved vs actual paid vs difference, with a warning if lower, and asks them to confirm the obligation is fully settled.Completed — even if paid < approved (e.g. ₹2,000 TDS handled outside the system on a ₹1,00,000 request).
Partial settlementSame comparison, flagged as a genuine part-payment.Partial · manager review → manager accepts & closes.
Order of operations

The payment saves only after the confirmation popup is accepted — there's no ambiguous "entered but not settled" limbo. One request is settled by one payment.

07 Keeping people informed

Notifications, reminders & conversation

  • In-app by default for every event, via the work queues.
  • Email is per-event configurable: enable/disable, fixed To/CC, optionally include the requester / selected manager / processing Accounts user, plus an editable subject and short message template. The approval email goes to Accounts + requester + a preconfigured management list.
  • Reminders: daily to the manager after 3 calendar days pending; a stale-processing nudge after 1 calendar day.
  • Urgent flag: immediate email to the manager (before approval) and to the configured Accounts/management list (after approval). It's only a flag + a notification — no special approval authority.
  • Conversation thread per request between employee, manager, and Accounts — visible to anyone who can view that request (a single shared thread, no hidden side-channel).
08 Where people work

Access & dashboard

Because a person may hold several roles, there is one dashboard with work areas — only the permitted ones appear: My requests, Manager approvals, Accounts queue, Administration.

  • No bulk approval — a manager opens the full request to decide.
  • Inactive projects/heads disappear from new selections but remain visible on historical requests.
  • Lists and reports export to CSV/Excel by permission.
09 Boundaries

Deliberately out of scope

Not in this version

No tax/TDS calculation (Accounts confirm deductions outside the system) · no recoverable repayment tracking (we record the expectation only) · no refund / return-of-money process · no forfeiture or write-off conversion · no direct request-less payments. Existing pre-go-live payments stay as historical records.

10 Delivery

How we'll build it

Phased so working software arrives early, each phase shippable on its own.

1

Roles & permissions foundation

Replace the two-role setup with the per-screen, data-scoped permission matrix, multi-role users, and create-by-copy. Everything else builds on this.

2

Request workflow

Mobile-first request form (treatment → type), auto numbering, submit / edit / return / reject / withdraw, the manager approval loop, the conversation thread, and the unified dashboard queues.

3

Payment linking & settlement

Atomic reservation from both entry points, Processing / On-hold, the settlement popup, and the partial → manager-review path.

4

Recoverables

The budget-expense vs recoverable classification, configurable categories, budget exclusion, and the recoverable payments report.

5

Notifications engine

Per-event email configuration, templates, the approval email, urgent alerts, and the reminder schedules.
